On-Device Multimodal Skill Agent with Execution-Grounded Retrieval and Per-Step Visual Verification

codename VESPER — Visually-verified, Execution-grounded Skill Procedure Execution & Retrieval

An on-device agent that retrieves and composes a multi-step skill from a shared text+image vector space, executes it one step at a time, verifies each step against the live device screen, and on visual failure re-retrieves and repairs — so retrieval relevance is grounded in real on-device visual execution outcomes rather than fixed at query time.

01

Proposed invention title

Primary: On-Device Multimodal Skill Agent with Execution-Grounded Retrieval and Per-Step Visual Verification.

Codename: VESPER — Visually-verified, Execution-grounded Skill Procedure Execution & Retrieval.

One-line: retrieval relevance is determined by on-device, per-step visual execution outcome — not by query-time similarity alone.

02

Executive summary

The existing on-device "Dynamic Skill" RAG takes a text query, performs hybrid retrieval over text-only SKILL.md chunks, and selects one skill for single-shot execution. It has three structural blind spots: it ignores the live screen (often the only real disambiguator), it discards visual content inside skill documents, and it never checks whether execution worked.

This invention restructures the system into a closed multimodal loop:

  1. Multimodal input — voice + text + a screenshot of the current screen — is fused into one query.
  2. A shared text+image embedding space indexes skills at step granularity; each step carries an instruction, a target image, and an expected-result image.
  3. An orchestration agent executes steps via heterogeneous backends (in-app / MCP / A2A) using dynamically synthesized actions (JSON/code).
  4. After each step a visual verifier embeds the new live screen and compares it to that step's expected-result image.
  5. On mismatch the system does two things together: synthesizes a corrected action and re-retrieves the next step using the current screen.
★ CORE The defensible novelty is item 5: retrieval driven by per-step on-device visual execution feedback, at step granularity. This differs from ordinary RAG (retrieve once, no feedback), corrective/agentic RAG (text-relevance feedback), and GUI agents (screen-checking without authored per-step visual success-conditions driving retrieval re-grounding).
03

Current system / existing RAG flow

Indexing (once): SKILL.md → Chunking (~2048 chars, section boundaries) → Embedding (768-dim, L2-normalized) → Storage: Room DB (skill_chunk), USearch (HNSW), FTS4 (skill_chunk_fts).

Retrieval (per query): query → Normalization → Vector Search (HNSW, M=16, efSearch=50, top-20) + BM25 (FTS4) → RRF Fusion (1/(60+vRank)+1/(60+bRank), k=60).

Selection: Section Boost (+20%/match, max +100%) → Disambiguation (−30% to −40%) → Aggregation (group by skill_path, SUM) → Selection (score > 0.02?) → return skill + routing JSON, else fallback.

[A0] Runtime assumed Android on-device; embedder assumed on-device ONNX (diagram states only "768-dim, L2-normalized").

Proposed invention and key novelty

Structural changes

  • C1 Multimodal input fusion: voice→text + text + screenshot-of-state → one query.
  • C2 Shared text+image embedding space (Version 2): one model embeds both; a text query natively retrieves image steps. On-device candidates exist (MobileCLIP2, SigLIP-2). [A1]
  • C3 Step-granular multimodal skills: step = {instruction, target image, expected-result image}.
  • C4 Heterogeneous, dynamically synthesized actions → in-app / MCP / A2A.

Key novelty ★ the claim sits here

  • N1 — per-step visual success-condition authored into the step, verified by embedding-similarity between live screen and expected-result image.
  • N2 — execution-grounded retrieval: on mismatch, re-retrieve the next/repair step using the current live screen.
  • N3 — mismatch-driven action repair: synthesize a different action, not a blind retry.
  • N4 — on-device step composition: the executed procedure is assembled from verifiable step primitives, possibly across skills.
★ Ordinary RAG retrieves once with no feedback; corrective/agentic RAG feeds back text relevance; GUI agents verify screens but without authored per-step visual success-conditions driving retrieval re-grounding at step granularity, on-device. The fusion of N1–N4 is the inventive step.

Detailed numbered technical workflow (input → final action)

  1. Receive input in any mix: voice, text, screenshot of current screen.
  2. Transcribe voice → text (if present).
  3. Capture/normalize the screenshot as the current screen-state image.
  4. Fuse text + screen-state into one query in the shared embedding space.
  5. Retrieve candidate steps/skills from the unified index (dense + lexical), with the live screen conditioning the ranking.
  6. Select / compose: pick a dominant skill, or have the Planner compose a step-set. Nothing clears confidence → fallback.
  7. Initialize step pointer N = 1.
  8. Synthesize the action for step N (JSON/code) from the step spec + current screen.
  9. Route the action to its backend (in-app / MCP / A2A) and execute.
  10. Capture the new live screen after execution.
  11. Verify: embed the new screen; compute similarity to step N's expected-result image.
  12. Match (≥ τ): advance N ← N+1; if more steps → step 8, else → step 16.
  13. Mismatch (< τ) → repair: (a) re-retrieve using the current live screen; (b) synthesize a different action; (c) re-execute (step 9). Bounded budget; exhausted → fallback/escalate.
  14. (Optional) Approval gate: high-risk actions require user confirmation before execution.
  15. Loop until all steps verify or budget exhausts.
  16. Goal reached: report success; optionally persist outcome for future ranking.

Use cases (example data & decisions)

Use case 1 — Multimodal happy path with one repair (WiFi)

Input: voice "I can't connect to WiFi" + screenshot = WiFi settings (failed). Routing: live WiFi screen reinforces connectivity → selected. Skill (5 steps): open WiFi → forget network → toggle off → toggle on → reconnect. Execution: step 2 "forget network" verify → mismatch → re-retrieve + corrected tap → match; remaining steps match. Outcome: goal reached; per-step repair fixed a failure single-shot would miss. See FIG. 5.

Use case 2 — Screen disambiguates a vague query (storage)

Input: text "fix this" + screenshot = storage-full warning. Today: words carry no signal → best skill < 0.02 → fallback. Invention: the screenshot vector sits near storage step-images → storage skill crosses threshold and is selected — the screen, not the words, made the pick. Counterfactual: same words on a battery-saver screen → battery skill. See FIG. 6.

Use case 3 — UI drift → re-retrieval + cross-skill composition ★

Input: text "turn off mobile data to save data" + screenshot = redesigned Settings (app updated; authored screenshots stale). Execution: step 1 verify vs stale image → mismatch (drift) → re-retrieve using the current screen → a step from a different skill's library matches the new UI → splice in → continue verified live. Outcome: the procedure that ran was composed at runtime across skills — impossible for whole-skill single-shot retrieval. Clearest demonstration of N2 + N4. See FIG. 7.

Complete request walkthrough & skill data model

This section makes the runtime concrete: (a) how a skill with image-steps is stored and embedded, (b) what happens end-to-end when a user asks, and (c) how the image-steps "react" during execution. Numbers below are illustrative (threshold τ shown as 0.82).

10.1 How a query is handled (lifecycle)

A request enters through one front door regardless of modality and is normalised into a single fused query before any retrieval happens:

  1. Arrive — input may be voice, typed text, a screenshot of the current screen, or any mix.
  2. Transcribe & capture — voice → text (ASR); the current screen is captured as a screen-state image.
  3. Fuse — text + screen-state are embedded into one query vector in the shared space.
  4. Retrieve — dense + lexical search over the unified index; the live screen conditions the ranking.
  5. Decide — pick a dominant skill, compose a step-set, or (if nothing clears confidence) fall back to plain LLM routing.
  6. Execute the step loop — per step: synthesize action → run via backend → verify against the step's expected-result image → advance or repair.
Query situationHow it is handled "properly"
Clear query, no screenshotText-only retrieval (degrades gracefully to today's behaviour) → skill picked.
Vague query + informative screenScreen vector lifts the correct skill over the threshold — the screen makes the pick.
Ambiguous, both signals weakNothing clears confidence → fallback to plain LLM routing (no wrong action forced).
Goal spans multiple skillsPlanner composes a step-set from primitives across skills.
Step fails mid-taskRe-retrieve with the live screen + synthesize a different action (repair), bounded budget.
UI/version driftVerification fails vs stale image → re-ground on the live screen and splice a matching step.

10.2 How image-step skills are stored for embedding

A skill is an ordered list of steps. Each step carries three things that are embedded into the same shared space, each with a distinct runtime role:

Step fieldPurposeEmbedded?Used for retrieval?Used for verification?
instruction (text)What the step doesYes (text→vec)Yes (dense + FTS4 lexical)No
target_imageWhat to act on (where to tap)Yes (image→vec)Yes (grounding the action)No
expected_result_image ★What success looks likeYes (image→vec)OptionalYes — the success oracle

Example skill as authored:

skill: connectivity.reset_network
steps:
  - id: s1   order: 1
    instruction: "Open Wi-Fi settings"
    target_image: s1_target.png            # the Wi-Fi entry to tap
    expected_result_image: s1_done.png     # Wi-Fi panel is open
  - id: s2   order: 2
    instruction: "Forget the saved network"
    target_image: s2_target.png            # the network row / Forget button
    expected_result_image: s2_done.png     # network removed from list
  - id: s3..s5  ...  (toggle off -> toggle on -> reconnect)

Where it lands at index time: the three vectors per step go into USearch (one shared vector index); step metadata + raw image assets + ordering go into Room (the skill_chunk table extended with chunk_type=step, step_order, asset_id, role); the instruction text goes into FTS4 for lexical recall. The expected_result_image vector is tagged role=verifier so it is available as the per-step success oracle at execution time, not only for retrieval. See FIG. 10.

reuse The stores (Room / USearch / FTS4) and their retrieval paths are reused; only the schema is extended and the embedder is swapped to the shared text+image model. [A3] assumes skills are authored with target and expected-result images.

10.3 Complete worked trace — "I can't connect to the Wi-Fi"

Voice query "I can't connect to the wifi" spoken while the phone shows the Wi-Fi screen with "Connection failed". τ = 0.82 (similarity threshold), illustrative numbers.

  1. Transcribe + capture — ASR → "I can't connect to the wifi"; screen captured → screen-state = Wi-Fi settings (failed).
  2. Fuse — text + screen-state → one query vector.
  3. Retrieve — shared-space search ranks connectivity.reset_network top (query↔skill similarity ≈ 0.88), well clear of other skills. The live Wi-Fi screen reinforces it.
  4. Select — connectivity clears confidence → its 5-step procedure is loaded; step pointer N = 1.
  5. Step 1 "Open Wi-Fi settings" — synthesize action {tap, target=s1_target} (grounded by the target image) → execute in-app → capture new screen → embed → similarity to s1_done = 0.91 ≥ τ → match → N = 2.
  6. Step 2 "Forget the saved network" — synthesize tap → execute → capture → similarity to s2_done = 0.64 < τ → mismatch (a confirm dialog appeared instead).
  7. Repair — re-retrieve using the current screen → fetch a corrected step (tap "Forget" in the confirm dialog) → synthesize a different action → execute → similarity = 0.88 ≥ τ → match → N = 3.
  8. Steps 3–5 (toggle off → toggle on → reconnect) — each executed, each verified against its expected-result image → all match.
  9. Goal reached — screen shows "Connected" → report success; optionally persist the outcome to inform future ranking.

A single-shot text RAG would have picked a skill (at best) and fired all five steps blind; the per-step visual check caught the Step-2 dialog and the repair recovered it. See FIG. 11; the runtime messaging is also in FIG. 8.

10.4 How image-steps "react" during execution

The two images attached to each step play opposite roles at runtime:

  • target_image → grounds the action. Before acting, the executor locates the step's target on the live screen (where to tap/where the control is) so the synthesized action lands on the right element even if positions shifted.
  • expected_result_image → judges the outcome ★. After acting, the new live screen is embedded and compared to this image; similarity ≥ τ means the step truly succeeded. This is the signal that drives advance-vs-repair, and it is what makes retrieval accountable to execution (N1–N2).
★ The expected-result image is not just another retrievable chunk — it is the per-step success oracle. Comparing the live screen against it (in the shared space) is the mechanism that converts a passive RAG into a closed, self-correcting loop.

High-level claim concepts (not final legal claims)

System concept

An on-device system comprising a shared text-image embedding index of skill steps, each step associated with a visual success-condition; a retriever that selects/composes steps from a fused query including a device screenshot; an executor that synthesizes and dispatches per-step actions to heterogeneous backends; a verifier that compares the post-action live screen to the step's visual success-condition; and a controller that, on a verification failure, re-retrieves a subsequent step using the live screen and synthesizes a corrected action.

Method concept

Capturing multimodal input including a device screen; retrieving/composing a multi-step procedure from a shared multimodal space; for each step synthesizing and executing an action, then verifying the resulting live screen against an authored visual success-condition; and on mismatch, re-retrieving using the live screen and synthesizing a different action, thereby grounding retrieval in visual execution outcome.

Dependent directions

Screen-conditioned ranking that lifts a candidate above a selection threshold; step-level composition across skills; graceful degradation to text-only when no screenshot is available; bounded repair/retry budget then fallback; optional approval gate for high-risk actions; backend selection among in-app/MCP/A2A; expected-result as image embedding verified by similarity threshold τ; integrity/version-drift handling via re-grounding.
